# Bump Version

Increment `version.toml` and generate a `CHANGELOG.md` entry from recent git history.
The `VERSION` file is regenerated as part of this skill (step 7) and again on the next
`bin/build.ps1` run or by running `python scripts\version.py` from the root of the project.

## Files

| File                 | Role                                                            |
| -------------------- | --------------------------------------------------------------- |
| `version.toml`       | version source of truth (three integers: major, minor, patch)   |
| `CHANGELOG.md`       | change history with dates, Keep a Changelog format              |
| `VERSION`            | flat file read by setuptools, generated by `scripts/version.py` |
| `scripts/version.py` | reads `version.toml`, writes `VERSION`                          |

## Workflow

### 1. Determine bump type

Ask the user which segment to bump if not already specified:

- **patch** -- backwards-compatible fixes and small additions.
- **minor** -- new capabilities, non-breaking.
- **major** -- breaking changes or major milestones.

### 2. Compute the new version

Read `version.toml` (format: `[version]` table with `major`, `minor`, `patch` integers).
Increment the chosen segment, reset lower segments to 0:

- patch bump: `2.0.1` -> `2.0.2`
- minor bump: `2.0.1` -> `2.1.0`
- major bump: `2.0.1` -> `3.0.0`

### 3. Gather changes from git

Run `git log` from the last commit that touched `version.toml` to HEAD:

```bash
git log --oneline --format="%h %s" $(git log -1 --format=%H -- version.toml)..HEAD
```

If there are no commits since the last version.toml change (i.e. this is the first bump or the bump is being done in the same commit batch), use judgment based on staged/unstaged changes and recent conversation context.

### 4. Draft the changelog entry

Format:

```
## [x.y.z] - YYYY-MM-DD

2-3 sentence summary of the release. what shipped, why it matters,
what area of the product it touches.

### added
- bullet: 1-2 sentences describing what was added.

### changed
- bullet: 1-2 sentences describing what changed.

### fixed
- bullet: 1-2 sentences describing what was fixed.
```

Only include sections (added/changed/fixed) that apply. Omit empty sections.

### 5. Style rules

These are non-negotiable:

- **Lowercase everything.** Headings, bullets, sentences. No title case.
- **ASCII only.** Straight quotes, hyphen-minus. No smart quotes, em-dashes, or ellipsis characters.
- **No hype.** No "exciting", "powerful", "robust", "seamless". Factual descriptions of what shipped.
- **No filler.** No "various improvements", "minor tweaks", "general cleanup". Be specific.
- **Area references.** Bullets should name the area of change (e.g. "worker backend", "cli", "persona sources", "frontend") not individual files.
- **Past tense or bare infinitive.** "added rate limiting" or "add rate limiting", not "adds rate limiting".

### 6. Present draft for approval

Show the user:

1. The new version number.
2. The drafted changelog entry.

Wait for approval or amendments before writing anything.

### 7. Write changes

On approval, execute these steps in order:

1. Update `version.toml` with the new integers (format: `[version]` table with `major`, `minor`, `patch` keys).
2. Prepend the new entry to `CHANGELOG.md` (after the `# changelog` header and description line).
3. Run `python scripts/version.py` to regenerate the `VERSION` file.

### 8. Verify

Read back `version.toml`, the top of `CHANGELOG.md`, and `VERSION` to confirm consistency.

## Examples

### Patch bump

User: "/bumpversion patch"

```
## [0.1.2] - 2026-05-04

fixed history validator edge case and tightened rate limit window.

### fixed
- history validator no longer repairs messages with missing role fields; rejects them instead.
- rate limit window narrowed from 60s to 30s for anonymous users.
```

### Minor bump

User: "/bumpversion minor"

```
## [0.2.0] - 2026-05-10

this would be a brief summary of the work that was accomplished.

### added

- x feature with y dependencies
- generated x plan for development

### changed

- fixed x bug that caused y issues with z
```

## Edge Cases

- **No commits since last bump:** ask the user what changed or whether the bump is intentional.
- **Multiple areas of change:** group bullets by area within each section, largest impact first.
- **Hotfix on main:** still follows this workflow. The changelog entry goes at the top regardless of branch.
